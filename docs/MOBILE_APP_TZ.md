# Техническое задание: мобильное приложение Self-Check Pro

## 1. Общие положения

### 1.1. Цель

Разработать мобильное приложение (iOS + Android) для исполнителей (`CLIENT_USER`), которое позволяет:

- авторизоваться в системе Self-Check Pro;
- менять пароль в профиле;
- просматривать список назначенных чек-листов;
- проходить чек-лист — заполнять ответы, прикреплять фото/видео/файлы и завершать работу.

### 1.2. Контекст

Существующее web-приложение — React 18 + Vite SPA. Бэкенд — Spring Boot, доступен через OpenAPI по адресу `frontend/src/resource/api.yaml`.

Базовый URL API: `/api/v1/`.  
В dev-режиме web проксирует `/api` на `http://localhost:8081`. Для мобильного приложения бэкенд будет доступен по отдельному адресу (уточняется DevOps).

### 1.3. Целевая роль

Мобильное приложение ориентировано на роль `CLIENT_USER` — исполнитель, которому назначены проверки.  
Роли в системе: `SYSTEM_ADMINISTRATOR`, `CLIENT_ADMINISTRATOR`, `CLIENT_USER`.

### 1.4. Требования к платформам

- **iOS**: минимум iOS 14, SwiftUI/UIKit по согласованию.
- **Android**: минимум Android 8.0 (API 26), Jetpack Compose/View по согласованию.
- Поддержка портретной ориентации (ландшафт — опционально для планшетов).
- Работа в условиях нестабильного соединения: graceful degradation, retry, индикация офлайн.

### 1.5. Технический стек (рекомендации)

- HTTP-клиент с interceptors (OkHttp / Alamofire или аналоги).
- Хранилище токенов — Keychain (iOS) / EncryptedSharedPreferences (Android).
- Локальное кэширование списка чек-листов и структуры шаблона — SQLite/Room/CoreData.
- Загрузка файлов — multipart с возможностью фоновой загрузки.
- Локализация — ru/en.

## 2. Общие требования к API-интеграции

### 2.1. Базовый URL и форматы

- База: `<backend>/api/v1/`.
- `Content-Type`: `application/json` по умолчанию.
- Для загрузки файлов: `multipart/form-data`.
- Даты:
  - date-only: `YYYY-MM-DD`;
  - date-time: ISO 8601 UTC с `Z`, например `2026-01-31T10:00:00.000Z`;
  - time: `HH:mm`.
- Все запросы, кроме `login` и `refresh`, должны содержать заголовок `Authorization: Bearer <accessToken>`.

### 2.2. Обработка 401 и refresh

Необходимо реализовать механизм, аналогичный web:

1. Access token хранится в защищенном хранилище.
2. Refresh token хранится в защищенном хранилище.
3. При получении `401` от API:
   - если это сам запрос `auth/refresh` — очистить токены и отправить пользователя на экран логина;
   - иначе выполнить `POST /auth/refresh` **без** Authorization-заголовка, с телом `{ refreshToken }`;
   - при успехе сохранить новую пару token/refreshToken и повторить исходный запрос;
   - при неудаче — очистить токены и перейти на экран логина;
   - параллельные запросы, упавшие с 401 во время обновления токена, должны ожидать завершения refresh и повторяться с новым токеном (single-flight + queue).

### 2.3. Обработка ошибок

- `400` — показывать сообщение из тела ответа, если есть; иначе общее сообщение об ошибке валидации.
- `401` — перенаправлять на логин (кроме случая refresh).
- `403` — показывать сообщение «Доступ запрещен».
- `404` — показывать сообщение «Не найдено».
- `409` — показывать глобальный тост с ошибкой.
- `413` — при загрузке файлов показывать сообщение о превышении размера.
- `429` — показывать сообщение о превышении лимита запросов и предлагать повторить позже.
- Network error — показывать индикатор офлайн и позволять повторить запрос.

## 3. Функциональный блок: Авторизация

### 3.1. Экран логина

Поля:

- Логин (`email`) — текстовое поле, клавиатура email.
- Пароль — поле с маскировкой, кнопка «показать/скрыть».
- Кнопка «Войти».
- Индикатор загрузки.

### 3.2. Логика

1. Пользователь вводит email и пароль.
2. По нажатию «Войти» выполняется `POST /api/v1/auth/login`.
3. При успехе сохраняются:
   - `accessToken` (ключ `token` для совместимости с web);
   - `refreshToken`;
   - данные пользователя (`users/me`).
4. Устанавливается заголовок `Authorization: Bearer <accessToken>`.
5. Переход на главный экран — список назначенных чек-листов.
6. При ошибке `401` — показывать сообщение «Неверно указаны имя пользователя или пароль».

### 3.3. Endpoint

`POST /api/v1/auth/login`

Тело:

```json
{
  "email": "user@example.com",
  "password": "secret"
}
```

Ответ `200`:

```json
{
  "accessToken": "eyJ...",
  "refreshToken": "eyJ...",
  "tokenType": "Bearer",
  "expiresIn": 3600,
  "refreshExpiresIn": 2592000,
  "permissions": ["..."],
  "role": "CLIENT_USER"
}
```

**Важно:** в web-поле ввода подписано «Логин», но в API передается `email`.

### 3.4. Восстановление сессии

При старте приложения:

1. Проверить наличие access token.
2. Если токен есть — установить заголовок и выполнить `GET /api/v1/users/me`.
3. При успехе — открыть список чек-листов.
4. При ошибке (401, 403, timeout) — очистить токены и показать экран логина.
5. Safety timeout для инициализации — до 7 секунд, после чего считать сессию недействительной.

### 3.5. Выход

По нажатию «Выйти» выполняется `POST /api/v1/auth/logout` (с bearer-токеном), затем очищаются локальные токены и кэш, пользователь возвращается на экран логина.

## 4. Функциональный блок: Профиль и смена пароля

### 4.1. Экран профиля

Отображать данные текущего пользователя, полученные из `GET /api/v1/users/me`:

- ФИО (`fullName`);
- Email (`email`);
- Организация (`organizationName`);
- Должность (`position.name`);
- Объекты контроля (`controlObjects[].name`);
- Роль (`role.name` / `role.nameEn` в зависимости от локали).

### 4.2. Смена пароля

Поля:

- Текущий пароль;
- Новый пароль;
- Подтверждение нового пароля.

Валидация на клиенте:

- все три поля заполнены;
- новый пароль совпадает с подтверждением.

### 4.3. Endpoint

`POST /api/v1/auth/change-password`

Тело:

```json
{
  "currentPassword": "old",
  "newPassword": "newSecret1",
  "confirmPassword": "newSecret1"
}
```

Ответ `200`:

```json
{
  "success": true,
  "message": "..."
}
```

Коды:

- `200` — пароль изменен;
- `400` — текущий пароль неверен или новый пароль не прошел валидацию (min 8 символов);
- `401` — не авторизован.

**Важно:** в web-коде функция `api.changePassword` не реализована, поэтому в мобильном приложении запрос нужно выполнять напрямую по спецификации.

## 5. Функциональный блок: Список назначенных чек-листов

### 5.1. Экран списка

Главный экран после авторизации — список чек-листов, назначенных текущему пользователю.

Каждая карточка должна отображать:

- название шаблона / задачи (`inspectionSchedule.name` или `template.name`);
- объект контроля (`controlObject.name`);
- статус (`status.code` + локализованное `description`);
- дату/время начала (`start_at`);
- дату/время окончания (`end_at`);
- кнопки действий (если применимо).

### 5.2. Фильтры и поиск

Поддерживаемые параметры запроса:

- `q` — поиск по задаче, объекту контроля, шаблону;
- `status` — `DRAFT`, `IN_WORK`, `COMPLETED`;
- `controlObjectId` — фильтр по объекту (camelCase);
- `template_id` — фильтр по шаблону;
- `user_id` — фильтр по пользователю (для «моих» чек-листов).

По умолчанию отображать чек-листы текущего пользователя (`user_id = <currentUserId>`). Если id недоступен — отправлять `user_id=me` (подтвердить поведение на бэкенде).

### 5.3. Пагинация

- Параметры: `page` (с 0), `size` (по умолчанию 10-20).
- Ответ Spring-стиля:

```json
{
  "content": [...],
  "totalElements": 42,
  "totalPages": 5,
  "size": 10,
  "number": 0
}
```

- Реализовать pull-to-refresh и подгрузку следующей страницы при скролле (pagination/infinity scroll).

### 5.4. Статусы и действия

Серверные статусы:

| Код | Локализованное отображение |
|-----|----------------------------|
| `DRAFT` | «Ожидание/В работу» (или производный UI-статус, см. ниже) |
| `IN_WORK` | «В работе» |
| `COMPLETED` | «Завершен» |

Производные UI-статуса для `DRAFT`:

- если `start_at > now` — «Ожидание», действия заблокированы;
- если `start_at <= now` — «В работу», доступна кнопка «Взять в работу».

Действия по строке:

- `DRAFT` + доступно время → «Взять в работу» → `PATCH /checklists/{id}/towork`;
- `DRAFT` / `IN_WORK` → «Завершить работу» → `PATCH /checklists/{id}/complete`;
- `COMPLETED` → «Возобновить работы» → `PATCH /checklists/{id}/towork`;
- тап по карточке открывает экран прохождения чек-листа.

### 5.5. Endpoint

`GET /api/v1/checklists`

Пример запроса:

```
GET /api/v1/checklists?user_id=12&status=IN_WORK&page=0&size=10&sort=start_at,desc
```

Структура элемента `ChecklistShortDto`:

```json
{
  "id": 101,
  "inspectionSchedule": { "id": 5, "name": "Ежемесячный обход" },
  "template": { "id": 8, "name": "Пожарная безопасность" },
  "controlObject": { "id": 21, "name": "Цех №1" },
  "inspector": { "id": 12, "name": "Иванов И." },
  "user": { "id": 12, "name": "Иванов И." },
  "status": {
    "code": "DRAFT",
    "description": "Ожидание/В работу",
    "descriptionEn": "Draft"
  },
  "start_at": "2026-01-31T10:00:00Z",
  "end_at": "2026-01-31T11:00:00Z",
  "created_at": "2026-01-31T09:00:00Z",
  "updated_at": "2026-01-31T09:30:00Z"
}
```

## 6. Функциональный блок: Прохождение чек-листа

### 6.1. Загрузка чек-листа

При открытии экрана прохождения:

1. Выполнить `GET /api/v1/checklists/{checklistId}` — получить чек-лист с уже заполненными ответами.
2. Если нужна структура шаблона отдельно — `GET /api/v1/templates/{templateId}`.
3. Выполнить `GET /api/v1/items/metadata` — получить справочник типов вопросов и их `settings_schema` (кэшировать на устройстве).

### 6.2. Структура чек-листа

Чек-лист состоит из секций (`sections`), каждая секция содержит элементы (`items`).  
Отображать только активные секции и активные элементы (`active !== false`).

`ItemDto`:

```json
{
  "id": 501,
  "name": "Есть ли огнетушитель?",
  "description": "...",
  "question_type": "boolean",
  "settings": { ... },
  "required": true,
  "photo_required": true,
  "video_required": false,
  "active": true,
  "order": 1
}
```

### 6.3. Типы вопросов и форматы ответов

Список типов динамический, определяется `GET /api/v1/items/metadata`.  
Основные типы, которые точно нужно поддержать:

| Тип | Компонент UI | Тип `answer` в payload | Примечания |
|-----|--------------|------------------------|------------|
| `text` | однострочное текстовое поле | `string` | — |
| `short_text` | однострочное поле | `string` / `null` | настройки: `min_length`, `max_length`, `placeholder` |
| `long_text` | многострочное поле | `string` / `null` | настройки: `min_length`, `max_length`, `placeholder` |
| `boolean` | кнопки Да / Нет | `true` / `false` / `null` | повторный тап снимает выбор |
| `number` / `numeric` | числовое поле | `number` / `null` | `min_value`, `max_value`, `unit`, `placeholder` |
| `double` | числовое поле с десятичной точкой | `number` / `null` | запятая нормализуется в точку; `precision`, `unit` |
| `slider` | слайдер | целое `number` / `null` | `min`, `max`, `step`, `label_start`, `label_end` |
| `single_choice` | радиокнопки / выпадающий список | `string` / `null` | `options[]`, `ui_hint` (`radio`/`dropdown`) |
| `multi_choice` | чекбоксы / чипсы | `string[]` / `null` | `options[]`, `min_selections`, `max_selections` |
| `date` | DatePicker | `YYYY-MM-DD` / `null` | `min_date`, `max_date` |
| `datetime` | DateTimePicker | ISO 8601 UTC с `Z` / `null` | `min_datetime`, `max_datetime` |
| `file` | загрузчик файлов | `string` (комментарий) | сами файлы — через `photo_ids`/`video_ids`/`other_ids` |

Для отображения используется поле `name` (при `required === true` добавлять маркер `*`).

### 6.4. Локальная модель ответа

На клиенте ответы хранятся в виде map по `item.id`:

```json
{
  "501": {
    "answer": true,
    "id": 9001,
    "photo_ids": [{ "attachmentId": 3001 }],
    "video_ids": [],
    "other_ids": []
  }
}
```

- `id` — id ответа с сервера (может отсутствовать для новых);
- `photo_ids`, `video_ids`, `other_ids` — массивы объектов `{ attachmentId: number }`.

### 6.5. Сохранение ответов

Сохранение выполняется по кнопке «Сохранить» (автосохранения нет).

Endpoint:

- создание: `POST /api/v1/checklists`;
- обновление существующего: `PUT /api/v1/checklists/{checklistId}`.

Тело запроса:

```json
{
  "template_id": 8,
  "control_object_id": 21,
  "start_at": "2026-01-31T10:00:00.000Z",
  "end_at": "2026-01-31T11:00:00.000Z",
  "answers": [
    {
      "id": 9001,
      "item_id": 501,
      "answer": true,
      "photo_ids": [{ "attachmentId": 3001 }],
      "video_ids": [],
      "other_ids": []
    },
    {
      "item_id": 502,
      "answer": "2026-01-31",
      "photo_ids": [],
      "video_ids": [],
      "other_ids": []
    }
  ]
}
```

Правила формирования `answers`:

- для каждого активного item активной секции создавать запись;
- если ответ пустой (`null`, `undefined`, пустая строка), поле `answer` не включается, но запись с `item_id` и пустыми массивами вложений отправляется;
- вложения нормализуются в массив `{ attachmentId: number }`;
- сохранять серверный `id` ответа, если он есть;
- сортировать по `item_id`.

### 6.6. Загрузка файлов

Загрузка выполняется через:

`POST /api/v1/attachments`

Формат: `multipart/form-data`

- поле `file` — бинарные данные;
- поле `filename` — обязательное строковое имя файла.

Ответ `201`:

```json
{
  "attachmentId": 3001,
  "filename": "photo.jpg",
  "contentType": "image/jpeg",
  "size": 1024000,
  "user": { "id": 12, "email": "user@example.com", "fullName": "Иванов И." },
  "coordinates": { "latitude": 55.75, "longitude": 37.61 }
}
```

После загрузки `attachmentId` добавляется в соответствующий массив ответа:

- фото → `photo_ids`;
- видео → `video_ids`;
- другие файлы → `other_ids`.

Требования:

- перед загрузкой изображений сжимать их (рекомендация: max 1 МБ, max 1920px, quality 0.8);
- максимальный размер файла — 10 МБ (по умолчанию из настроек item);
- поддерживать выбор нескольких файлов;
- показывать прогресс загрузки;
- при ошибке `413` — сообщение «Файл слишком большой».

### 6.7. Удаление файлов

При удалении вложения из UI:

- удалить из локальной модели ответа;
- пометить `attachmentId` как удаленный;
- при следующем `PUT /checklists/{id}` не включать удаленный id в массивы;
- опционально вызывать `DELETE /api/v1/checklists/{checklistId}/answer/{answerId}/attachments/{attachId}` или `DELETE /api/v1/attachments/{attachId}` для немедленного удаления на сервере (уточнить у бэкенда).

### 6.8. Завершение и возобновление

- «Взять в работу» / «Возобновить»: `PATCH /api/v1/checklists/{id}/towork` → статус `IN_WORK`.
- «Завершить работу»: `PATCH /api/v1/checklists/{id}/complete` → статус `COMPLETED`.

Оба endpoint без тела.  
При `400` на `complete` показывать сообщение «Заполненный лист имеет ошибки, перед отправкой необходимо заполнить все данные».

Для завершенных чек-листов:

- скрывать кнопку «Сохранить»;
- разрешить просмотр ответов;
- разрешить «Возобновить работы».

### 6.9. Валидация ответов

Ошибки валидации приходят в поле `answerValidationErrors`:

```json
[
  {
    "itemId": 501,
    "itemName": "Есть ли огнетушитель?",
    "errors": ["Обязательный вопрос"]
  }
]
```

Требования:

- отображать ошибки под соответствующим вопросом;
- при попытке завершения чек-листа с ошибками скроллить к первому ошибочному вопросу;
- клиентская валидация обязательных полей (required), диапазонов чисел/дат, количества файлов.

### 6.10. Офлайн-режим (рекомендации)

API не поддерживает частичное сохранение — отправляется весь массив `answers`. Поэтому офлайн-черновик нужно проектировать с нуля:

- кэшировать структуру шаблона и текущие ответы в локальной БД;
- при восстановлении связи отправлять `PUT /checklists/{id}` целиком;
- показывать индикатор «не синхронизировано»;
- конфликт-резолюцию (если данные на сервере изменились) — по возможности перезаписывать локальными, либо предлагать пользователю выбор.

## 10. Особенности и ограничения

1. **Смена пароля**: в web-коде отсутствует реализация вызова `change-password`. Мобильное приложение должно выполнять запрос напрямую по спецификации.
2. **Нет endpoint'а «мои чек-листы»**: используется фильтр `user_id`. При отсутствии id пользователя web шлет `user_id=me` — нужно подтвердить поддержку на бэкенде.
3. **Нет автосохранения**: сохранение только по кнопке. Офлайн-черновик проектируется отдельно.
4. **Удаление вложений**: web не вызывает `DELETE` на сервер сразу, а отвязывает через `PUT`. Уточнить у бэкенда политику очистки осиротевших файлов.
5. **Смешение naming**: часть полей в snake_case (`start_at`, `item_id`, `photo_ids`), часть в camelCase (`controlObject`, `attachmentId`, `organisationId`). Важно не путать.
6. **Динамические типы вопросов**: список `question_type` приходит из `GET /api/v1/items/metadata`, а не зашит в коде.
7. **Статусы**: сервер возвращает объект `{ code, description, descriptionEn }`; UI-статусы «Ожидание» / «В работу» для `DRAFT` вычисляются клиентом по `start_at`.
8. **Роли**: `AuthResponseDto.role` — строка, `UserResponseDto.role` — объект. Нужна нормализация.
9. **Расхождения в API**: см. открытые вопросы ниже.
